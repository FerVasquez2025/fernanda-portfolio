The challenge

The product had evolved faster than its UI system.

As Playvox expanded, teams were solving similar interface problems in different ways. Patterns were duplicated, implementation details drifted, and designers and engineers did not always share the same source of truth.

The goal was not simply to build a Figma library. It was to create a system that could survive product scale and remain synchronized with production.

01

UI inconsistency

Similar interactions appeared with different styling, spacing and behavior across the platform.

02

Design–code drift

Figma and production components could diverge over time, creating uncertainty about which version was correct.

03

Repeated decisions

Teams repeatedly solved interaction and visual problems that should have already been standardized.

My role

Designing both the system and how teams used it.

I led the redesign of the design foundations and component experience in Figma while partnering closely with Front-end engineers to translate the system into reusable production components.

My responsibility extended beyond component design. I documented behavior, responsive rules, accessibility considerations and usage guidance, and regularly audited implementation against the design source.

Documentation

A component is not finished when the UI is finished.

Each pattern needed enough context for another designer or engineer to apply it correctly without having to ask the original creator.

Documentation became part of the component itself rather than an afterthought.

Anatomy

What makes the component.

Parts, spacing, sizing and structural relationships were clearly identified.

Behavior

How it responds.

States, interaction behavior and responsive adaptation were documented alongside visuals.

Guidance

When to use it.

Use / don’t use guidance reduced misuse and helped teams make consistent design decisions.

Design ↔ Engineering

Creating one shared source of truth.

I partnered closely with Front-end engineers so the design system was not limited to Figma. Components were recreated as reusable production components and documented in Storybook.

Chromatic provided versioning and visual review, helping us detect regressions and compare implementation against approved design behavior.

Governance

Keeping design and production aligned over time.

A design system only stays useful if someone actively protects its quality. Governance became part of the workflow rather than a one-time cleanup exercise.

01

Design review

New patterns were evaluated against existing components before introducing another variant or interaction.

02

Implementation audit

I periodically reviewed production components to identify visual or behavioral differences between Figma and Storybook.

03

Versioning

Storybook and Chromatic made changes traceable, allowing Design and Engineering to understand when a component had evolved.

04

Continuous documentation

Guidance evolved alongside components so teams could continue using the system without relying on tribal knowledge.
